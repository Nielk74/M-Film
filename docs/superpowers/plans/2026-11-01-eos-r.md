# EOS R Experimental Port Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans for inline implementation and a fresh whole-branch review.

**Goal:** Produce a tested, cross-compiled EOS R port attempt with explicit hardware and CR3 limitations.

**Architecture:** Keep the shared Film OS and old-camera entry point. Adapt the camera host for RGBA and the newer ML Picture Style API. Build R.180 separately against a pinned core.

**Tech Stack:** C99, Python unittest, Bash, ARM GCC, Ubuntu 24.04.

**Spec:** ../specs/2026-11-01-eos-r-design.md

## Global Constraints

- Original EOS R only: firmware 1.8.0, internal 7.3.9.
- ML revision 142472e95054d73640f50789ac0fd66325499d82 for R.180.
- Preserve upstream property restrictions and other bodies' build path.
- No firmware flash, installer, release or hardware-supported claim.

## Review Focus

- RGBA surface ownership across UI open/close and HUD redraws.
- No legacy palette access in the preprocessed EOS R host.
- Six-slider Picture Style API and no ISO/WB/remote-shutter write expansion.
- CR3 logs and no accidental use of the CR2 developer.
- Correct default settings filename and boot reservation accounting.

## Decisions

Keep EOS R outside the normal supported camera/release matrix. UI startup, HUD
and playback locking default off in developer files. CR3 development remains
explicitly unavailable; the proprietary Darkrooms application is not assumed to
support it. The user's camera is available for subsequent testing; its installed
firmware revision has not yet been read.

Verification: eight host tests pass, including 19 scenes and both CR2 channel
layouts with exact native/ARM-alignment print equality. Both ARM builds pass.
Ruling: the EOS R has no verified AE_VALUE implementation, so omit the meter
needle rather than invent a hardware address. Cost: this HUD element is absent
until upstream supplies a verified source. Picture Style timeout now prevents
editing the previously selected style; its regression was observed RED then GREEN.
